## 一、先搞清楚:向量数据库站在整个链路的哪个位置

学任何东西之前,先知道它在全局的哪里。RAG(检索增强生成)的完整链路:

```
  离线阶段(建库,跑一次)
  ┌────────────────────────────────────────────────────────────┐
  │  原始文档 → 切分(Text Splitter)→ 分块                      │
  │         → 嵌入模型(Embedding Model)→ 向量                  │
  │         → 灌入向量数据库(FAISS / Milvus / pgvector)  ← 你在这 │
  │         同时把原文+元数据存进普通数据库                       │
  └────────────────────────────────────────────────────────────┘

  在线阶段(每次提问都要跑)
  ┌────────────────────────────────────────────────────────────┐
  │  用户提问 → 嵌入模型 → 查询向量                             │
  │         → 向量库检索 Top-K  → 拿到原文片段            ← 你在这 │
  │         → (可选)Reranker 精排 → 拼进 Prompt → 大模型 → 回答  │
  └────────────────────────────────────────────────────────────┘
```

**关键认知:向量库只是中间一段。**
检索效果不好时,90% 的原因不在向量库选型,而在**切分方式**和**嵌入模型**。
FAISS 换成 Milvus 基本不会让回答变好;切分方式改一下往往会。

所以这一课的定位:**把"检索"这一段彻底搞明白**,它是整条链路里唯一你完全可控、且性能可以直接量化的部分。

## 二、前置知识(往下走之前得会这些)

| 知识点 | 要会到什么程度 | 补课方向 |
|---|---|---|
| Python 基础 | 类、继承、装饰器、类型注解 | 你已具备 |
| numpy 基础 | 数组形状 `(N, D)`、矩阵乘法、`np.linalg.norm` | 重点补:广播、`ascontiguousarray` |
| 线性代数直觉 | 向量、点积、范数、余弦相似度 | **不用会证明,要会算**,能读懂 `cos = a·b/(\|a\|\|b\|)` 就够 |
| LangChain 基础 | LCEL 链、Document 对象、Runnable 协议 | 你已学(第 1~19 课) |
| HTTP / JSON | 调用嵌入模型 API 的入参出参 | 你已具备 |

**其中最容易忽视的是线性代数直觉。** 不需要啃教材,只需要建立三个画面:

1. **向量 = 空间里的一个箭头**。方向代表语义,长度代表"强度"。
2. **点积 = 两个箭头有多对齐**。同向最大,垂直为 0,反向为负。
3. **余弦相似度 = 点积去掉长度影响**,所以只剩"方向像不像",取值 -1 ~ 1。

有了这三个画面,"归一化后内积等于余弦相似度"就是显然的,不用背。

## 四、进阶知识清单(接下来按顺序学)

### 阶段 1:切分与嵌入 —— **优先级最高,收益最大**
- [ ] `RecursiveCharacterTextSplitter` 的 `chunk_size` / `chunk_overlap` 怎么定
- [ ] 中文切分和英文切分的差别(中文要按标点+语义边界,不能照抄按空格切)
- [ ] 按语义切分(按段落、按标题层级、按 Markdown 结构)
- [ ] 中文嵌入模型选型:`BAAI/bge-small-zh-v1.5`(小)、`bge-large-zh-v1.5`(大)、`bge-m3`(多语言)
- [ ] 怎么**量化**一个嵌入模型好不好(建个小测试集,看命中率)
- [ ] **换嵌入模型 = 必须重建全部索引**,这是最大的运维成本,要提前规划

### 阶段 2:完整 RAG 链路与调优
- [ ] 把本课的检索段接到你项目的 `app_handler.py` 里,做成真正的 RAG
- [ ] Prompt 里怎么组织 context(编号、来源标注、怎么教模型"不知道就说不知道")
- [ ] 引用溯源:回答里标出引用了哪几段资料
- [ ] 多轮对话 + RAG 怎么结合(检索时要拼接历史吗?)
- [ ] 流式输出(你项目现在是同步返回,改成 SSE 体验会好很多)

### 阶段 3:混合检索与精排
- [ ] **BM25 + 向量检索** 混合:向量擅长语义,BM25 擅长专有名词/型号/编号,两者互补
- [ ] 融合策略:RRF(Reciprocal Rank Fusion)加权合并
- [ ] **Reranker 精排**:先用向量库粗召回 Top-50,再用 Cross-Encoder 模型精排到 Top-5
      (典型模型:`BAAI/bge-reranker-base` / `bge-reranker-v2-m3`)
- [ ] 什么时候需要 Reranker(自测:召回够但**排序不对**时)

### 阶段 4:生产级向量库
- [ ] **pgvector** —— 你项目已经在用 PostgreSQL,加个扩展就能用,迁移成本最低
- [ ] **Milvus** —— 分布式、千万级以上的选择,运维复杂
- [ ] **Qdrant** —— Rust 写的,单机性能好,API 友好
- [ ] 选型要考虑:数据量、并发、能不能接受独立部署一个服务、要不要和现有数据库事务一致
- [ ] 增量更新与删除策略(数据天天变,索引怎么跟上)

### 阶段 5:评估(不然调优全靠玄学)
- [ ] 建评估集:一批「问题 → 应该命中的文档」的标注对
- [ ] 指标:召回率@K、命中率、MRR、NDCG
- [ ] 端到端评估:回答是否忠于资料(忠实度)、是否答到点上(相关性)
- [ ] 用 LangSmith 做实验追踪(你 `.env` 里已经配了 `LANGSMITH_API_KEY`,可以开始用了)

## 五、本课实测踩到的 5 个坑(都是真跑出来的,建议收藏)

### 坑 1️⃣ `IndexFlatL2` 返回的是**平方**距离
```python
# (0,0) 到 (3,4),真实欧氏距离 5.0
index.search(...)  →  25.0     # 平方后的值!
```
**影响**:排序不受影响(单调),但拿距离做**阈值判断**时会判错。
比如你以为设了"距离 > 1.2 就不相关",实际在比较平方值,阈值完全不是那个意思。

### 坑 2️⃣ `similarity_search_with_relevance_scores` 的分数会骗人
实测两种策略都出问题:

| 策略 | 问题 | 实测现象 |
|---|---|---|
| `EUCLIDEAN`(默认) | 公式按**未平方**距离除 `sqrt(2)`,但 FAISS 给的是平方值 | 最相关文档得分 **-0.1314**(负数!) |
| `MAX_INNER_PRODUCT` | 公式算 `1 - x` 把**相似度**当成距离,排序整个反转 | 最相关 0.42,最不相关 0.71 |

源码在 `langchain_core/vectorstores/base.py`:
```python
def _euclidean_relevance_score_fn(distance):        return 1.0 - distance / math.sqrt(2)
def _max_inner_product_relevance_score_fn(distance): return 1.0 - distance
```
两个参数都叫 `distance`(暗示越小越好),但 IP 策略下传进来的其实是**相似度**。

**结论**:用 `similarity_search_with_score` 拿原始分数自己判断方向,
或者构造时传 `relevance_score_fn=` 把自己的规则写死。

### 坑 3️⃣ Windows 上 FAISS 遇到中文路径直接报错
```
RuntimeError: ... FileIOWriter(const char *) ... could not open
C:\...\23-faiss向量数据库的配置与使用\storage\raw_flat.index for writing
```
`write_index` / `read_index` 的路径在 C++ 层是 `const char*`,不认非 ASCII。
**同样受影响的还有 LangChain 的 `save_local` / `load_local`**(内部就是调的它)。

**解法**:改用 `faiss.serialize_index()` 拿 numpy 数组,由 Python 写文件:
```python
with open(path, "wb") as f:
    f.write(faiss.serialize_index(index).tobytes())
# 读回
index = faiss.deserialize_index(np.frombuffer(open(path,"rb").read(), dtype="uint8"))
```
LangChain 那边同理,`.pkl` 用 `pickle.dump((vs.docstore, vs.index_to_docstore_id), f)`。

> ⚠️ 手动重建 `FAISS(...)` 时,**不会**恢复 `distance_strategy` / `normalize_L2` /
> `relevance_score_fn`,要自己再传一遍,否则会静默退化成默认的 `EUCLIDEAN_DISTANCE`。

### 坑 4️⃣ 用 Python 内置 `hash()` 做特征哈希 → 重启后索引全废
`hash("字符串")` 每次进程启动的种子都不同(`PYTHONHASHSEED` 随机化),
存进磁盘的索引下次加载,同样的文本算出的是**不同的向量**,检索结果完全错乱。
**要用 `zlib.crc32` / `hashlib.md5` 这类稳定哈希。**
(这个坑在生产里踩一次要查很久,因为代码看起来完全正确。)

### 坑 5️⃣ 向量长度偏差会扭曲排序
教学用的词袋模型一开始用词频,结果查 `"FAISS 是什么"` 排第一的是讲 HNSW 的文档
—— 因为它更短、向量更集中,更容易和短查询"对上"。
改成 0/1 记存在性后正确答案才浮上来。

**真实嵌入模型也有这个偏差**(长文档的向量会被"稀释"),
所以生产上通常会:对结果做长度归一化、或者上文提到的 Reranker 精排。

### 附:两个 API 层面的细节
- **`k` 大于库容量时补 `-1`**:直接拿去索引列表会命中**最后一条**(Python 负索引),
  是个静默 bug,一定要判 `!= -1`。
- **`.pkl` 是 pickle**:反序列化会执行代码,所以 `load_local` 强制要求
  `allow_dangerous_deserialization=True`。
  **永远不要加载别人给的 `.pkl` 文件。**

## 六、推荐学习顺序(有时间线)

```
  ✅ 现在      FAISS 基础(本课)              —— 1 天
  ⬜ 第 1 步    文本切分 + 中文嵌入模型        —— 2 天  ← 收益最大,别跳过
  ⬜ 第 2 步    把 RAG 接进 llmops-api        —— 2 天  ← 有产出,能做 demo
  ⬜ 第 3 步    混合检索 + Reranker           —— 2 天
  ⬜ 第 4 步    评估方法 + LangSmith          —— 1 天  ← 让调优有依据
  ⬜ 第 5 步    pgvector(你已有 PG)          —— 2 天
  ⬜ 第 6 步    按需上 Milvus / Qdrant        —— 用到再说
```

**不要做的事**:
- ❌ 一上来就上 Milvus —— 会淹死在运维细节里,而核心概念还没建立
- ❌ 纠结索引选型 —— 2 万条以内用 Flat,把时间花在切分和嵌入模型上
- ❌ 凭感觉调参 —— 先建评估集,不然你永远不知道自己改的是变好还是变坏

## 七、下一步动手建议

给你项目(`llmops-api`)的具体改造路径:

1. **加依赖**:`faiss-cpu`(已装)+ `langchain-huggingface` + `sentence-transformers`(本地中文嵌入,免费不联网)
2. **新增服务** `internal/service/vector_store_service.py`:把本课的封装抽成服务
3. **新增数据模型**:一张表存「文档块原文 + 元数据 + 向量库里的 id」,和 FAISS 索引一一对应
   (这就是本课反复强调的"原文和元数据要自己存")
4. **改造 `app_handler.py` 的 `debug`**:把现在的纯对话链换成 RAG 链
   (本课第 6 部分的代码可以直接抄)
5. **加两个接口**:`POST /dataset/<id>/document`(上传并建索引)、`POST /app/<id>/debug`(带检索的对话)

第 3 步是最容易被忽略的:**FAISS 只管向量,原文得存在你自己的 PostgreSQL 里。**
本课示例用 `CORPUS` 列表代替了这张表,真实项目里它得是个正经的表。
